## Correction to the headline interpretation

This was a mixed diagnostic smoke suite, not a temporal-accuracy benchmark. Restricting the
answers to the owner-change and late-arrival scenarios gives **Graphiti 7/7, LightRAG append
7/7, and LightRAG replace 5/7**. The two Graphiti launch-date misses were retrieval coverage
failures outside that temporal subset. The original overall score does not establish that
LightRAG handles changing facts more accurately. The initial evidence inputs also had no
shared answer-token cap and included duplicated LightRAG storage metadata.

The dashboard now labels temporal and other dimensions separately. New runs use normalized,
budgeted answer evidence and can use the controlled temporal stress suite described in
[temporal-benchmark.md](temporal-benchmark.md). These methodology changes mean a new run is
not directly comparable to the old overall score. The original JSON and answers remain unchanged.

## What this says about updates

**Graphiti preserved the valid-time transitions.** After the new Project Atlas owner arrived, it answered both the current and January ownership questions. It also handled a February record ingested after a March record: the March owner remained current, while January and February owners were still retrievable at their dates. The report exposes the returned facts' validity intervals and source episode ids.

The native intervals were not perfectly conflict-free: the February historical search returned both Bob’s February-to-March fact and Alice’s older fact with an end date of March 1. The answer model chose the correct later fact. Graphiti’s interval filtering therefore reduced obsolete evidence here, but did not eliminate every overlap after an out-of-order update.

**LightRAG append also answered those questions correctly.** Keeping the dated source versions gave the shared answer model enough context to resolve chronology. It exposed more obsolete values in retrieval. This demonstrates that date reasoning over source text can work, even without an interval filter in storage.

**LightRAG replace lost useful information on a late arrival.** Replacing the March source with the subsequently received February record removed the evidence for the current owner and January owner. It abstained on those two questions. This is a limitation of the harness's arrival-order replacement policy, not proof that an application built on LightRAG cannot implement effective-date ordering or snapshot catalogs.

**Graphiti's fact-edge search missed a single-entity attribute.** Both launch-date probes returned no evidence. The ingestion result contained one entity and zero fact edges. Inspecting Neo4j showed a Beacon 2.0 entity summary containing the initial launch date, while the fact-edge adapter had nothing to return. A broader Graphiti node/episode retrieval path or a typed ontology would be a separate experiment; the harness did not change the retrieval policy or gold labels to improve this score. These misses should not be read as evidence that temporal invalidation itself failed.

**All three removed the deleted escalation code and preserved the shared support-channel fact.** For the unsupported code question, Graphiti abstained. Both LightRAG tracks retrieved the remaining support-channel information, and the shared answer generator incorrectly treated that channel as an escalation code. Those answers failed the gold check even though neither contained the deleted code. This is a grounding/retrieval-context failure rather than evidence that document deletion failed.

The measured strength of Graphiti here is explicit dated fact transitions with narrower temporal retrieval. The best overall answer count in this small suite came from LightRAG append. A larger representative dataset, broader Graphiti retrieval, and repeated runs should precede a product choice.
